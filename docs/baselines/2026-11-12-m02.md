2026-11-12, Windows 11, existing Python 3.14 environment; base: M02 base.
Production code, then a tester phase: nine `known_defect` markers (#44, #49 x2, #52, #55, #56, #57,
#62, #73) are removed and kept as regression guards; new tests are `tests/test_m02_storage.py` (23),
`tests/test_m02_media_names.py` (12), `tests/test_frame_text_copies.py` (26) plus crypto tests in
`tests/test_crypto.py` and `tests/test_defects_privacy.py`. All stores were disposable
encrypted databases; no user history, keyfile or data directory was opened. No dependency added.

## FK-deletion benchmark (disposable encrypted store)

Synthetic `audio_segments` where every second row continues the previous one; `delete_spent_segments`
(batches of 500) on one connection while a second connection inserts a row every 10 ms. Script was a
throwaway in the session scratchpad. BUSY_TIMEOUT_MS is 5000.

| Rows | Index | Delete time | Worst concurrent insert wait |
| --- | --- | --- | --- |
| 5 000 | none (v19) | 0.75 s | 0.77 s |
| 5 000 | 0020 | 0.06 s | 0.06 s |
| 50 000 | none (v19) | 75.1 s | concurrent insert failed: `database is locked` after the 5 s timeout |
| 50 000 | 0020 | 0.59 s | 0.65 s |

A 200 000-row run was started and stopped (the unindexed case does not finish in useful time).
Conclusion: without the index, deletion is quadratic and starves writers beyond the busy timeout;
with it the wait stays far below the timeout. One machine, one run each.

`delete_all_recorded_data` with 20 000 synthetic `audio_segments` and a concurrent writer:

| Index | Delete time | Concurrent writer worst wait |
| --- | --- | --- |
| none (v19) | 12.19 s | above `BUSY_TIMEOUT_MS`; an insert failed |
| 0020 | 0.22 s | 255 ms |

In that setup `delete_spent_segments` removed 0 rows, so these rows measure the full-deletion path
only.

## Decisions

- Argon2 ceilings: memory 1 GiB (4x the 256 MiB default), time 10 (over 3x), lanes 16 (4x). The app
  only ever writes the default; the ceilings stop a tampered keyfile from forcing huge work.
- Bad or outside-store media path in retention: skip, keep the reference, log the exception type
  only, count separately; per-category delete returns 409 while such references remain (user,
  2026-11-12).
- Deviation: the "references remain" check applies to `screenshots` and `raw_audio` only. For
  `frame_text` and `transcripts` the screenshot or audio is meant to stay, so remaining
  references are normal there. The check also ignores rows the purge deliberately keeps (queued OCR
  or speaker work), by sharing the purge's own selection.
- Legacy provenance: an answer citing a frame that is missing, has no text, sits at another
  timestamp, or whose sources have an unknown kind is cleared with its later replies, once.

## Accepted points

No user history was opened. Deletion is invalidation, not secure erasure of disk blocks. DST
behavior is validated only synthetically (distinct UTC instants give distinct names); no real clock
change was observed. Collision handling assumes a single writer per media directory.

## Gaps

A drive-qualified reference such as `C:/outside.webp` resolves inside the media directory on a
same-drive Windows store, so it is not counted as a bad path (#56, #73). M02.1 stays open until it
is fixed or accepted as a limit.

## Downstream contracts

- M02.1 to M03, M04, M06A, M07A, M08, M12, M13, M20: use `db.transaction()` for all writes, expect
  the continues index, and treat `bad_media_paths`/`locked_media_files` as count-only keys.
- M02.2 to M13A: thumbnails are keyed by frame id, image path and width and cleared on deletion.
- M02.4 to M15B: unlock work is bounded by `_MAX_ARGON2`.
