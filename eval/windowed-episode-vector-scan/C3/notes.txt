Mechanism
  windowed (start_ms > 0 or end_ms < 2**62) and |allowed| <= K:
    SELECT rowid, owner_id, start_ms, vec FROM embeddings WHERE owner_kind='episode' AND model=?
      AND owner_id IN (SELECT value FROM json_each(?))
    plan: SEARCH embeddings USING INDEX sqlite_autoindex_embeddings_1 (owner_kind=? AND owner_id=?
      AND model=?) + LIST SUBQUERY over json_each. No ORDER BY, no join, membership from ids only.
  otherwise: today's statement (same WHERE, plus rowid and start_ms columns), today's 4000-row chunks.
  No schema change, no prepare(), no new dependency, encryption untouched.

Fix round (cand.py): reproduce today's float32 matrices exactly instead
  Today's scan reads embeddings_time in (start_ms, rowid) order, 4000 rows per fetchmany, then drops
  non-allowed / wrong-size rows; each chunk's survivors are one float32 matrix. The probe returns
  every allowed row with (start_ms, rowid); the chunk boundaries that fall between the first and
  last probed key come from the covering index embeddings_time:
    SELECT count(*) ... AND start_ms < <first probed start>              (index-only, O(rank))
    SELECT start_ms, rowid ... AND start_ms >= ? ORDER BY start_ms, rowid LIMIT 1 OFFSET ?
                                                                         (one per boundary, O(span))
  Each chunk group is scored as today (f16 -> f32 matrix @ q) => bitwise today's scores. Order =
  (-score32, start_ms, rowid), which equals today's stable insertion order at equal float32 scores.
  Then runs of exactly equal float64 per-row dots (identical vectors) that are adjacent in that order
  are re-sorted by (start_ms, rowid); float64 dots are computed only for the top limit+64 pool.
  Result: mismatches=0 (hard 0, near_tie 0, tie_order 0; today vs itself had 14 tie_order),
  max |dscore| = 0 (62,852 owners compared, all bitwise equal).

K fit (linear cost model probe(k) = a + b*k vs scan(k) = c + d*k, fitted on k = 10, 100, 1k, 2k, 5k;
warm median of 7; "window" ids = a contiguous newest-first slice of episodes, "random" = uniform ids)
  final cand.py (fit_k.log):
    probe(window) = 0.670 ms + 2.212 us*k   probe(random) = 4.063 ms + 10.469 us*k
    scan          = 93.745 ms + 0.056 us*k
    crossover K: window 43,171   random 8,612
  first try (f64\fit_k_f64.log): window 27,657   random 9,186
  Chosen K = 9,000: the worst-locality fit (random ids), rounded. The window-layout fits overshoot:
  probe cost turns superlinear past ~5k ids once the 2 MB page cache overflows (each probe then
  decrypts a page), so direct measurements put the true crossovers at about 25k (window) and
  13k (random) for cand.py. K = 9,000 sits below every measured crossover in both sweeps:
    k=10,000: probe 42.6 (window) / 85.3 (random) ms vs scan 96.6 ms.
  The random-id knee (2.3 ms at 1k -> 34 ms at 2k) is page-cache overflow, not a planner change.

Costs and limits to weigh
  - Replay overhead is index-only but O(history) / O(span): one count(*) up to the first probed key
    (0.13 ms at 5.5k rows, 0.52 ms at 21.7k, 0.94 ms at 39.7k, warm) plus one OFFSET walk per
    crossed chunk boundary. 10 random ids spread over two years cost 2.7 ms (first try: 0.03 ms).
    At ~10x history (400k episodes) the count alone would be ~9 ms warm: then the first try
    (float64, near-tie order may differ from today's float32 order) is the scalable choice.
  - The replay depends on today's CHUNK_ROWS, today's scan statement and OpenBLAS sgemv giving the
    same result for the same matrix (verified here: 0 score differences). It reproduces an
    artifact, not a semantic; if today's code changes, the exact-order target moves with it.
  - Day / straddle windows include long episodes that start days before the window; their keys
    widen the probed span (day scenario: first probed start 14 days before the window, 2,617-row
    boundary walk), which is why the replay day p50 is 0.6 ms vs 0.09 ms for the first try.
  - Fails over to the full scan when a windowed question has > K candidates (one-year windows of
    ~20k episodes): probe would still be faster there for window-shaped ids (83 vs 105 ms at 20k).
  - A future ORDER BY or join on the probe statement could switch the planner to embeddings_time
    (full scan); plans.txt shows the autoindex probe for every traced windowed statement.
